# ADR-0005：数据接入与部署（v1）

- **状态**：已接受（2026-08-17）
- **来源**：wayfinder 票 [#11 数据接入与部署](https://github.com/0xnicholas/heirloom-pro/issues/11)，父图 [#1](https://github.com/0xnicholas/heirloom-pro/issues/1)
- **输入**：[ADR-0002](0002-storage-engine-mapping.md)（#7：引擎写入通道、水位线轮询）、[ADR-0003](0003-action-semantics.md)（#8：导入不经动作、批量 ≤1000）、[ADR-0004](0004-minimal-security-model.md)（#9：服务账号/PAT、超管引导、管理 API 面）
- **关系**：兑现 ADR-0003 后果段「批量导入走引擎写入通道」与 ADR-0004 后果段「导入用服务账号 + 超管签发 token」对 #11 的移交

## 背景

根决策锁定：自部署单租户、SDK+API 是第一界面、v1 无 UI、单 Postgres。Palantir 的数据接入是第一支柱（Data Connection 同步器托管运行），Heirloom 每支柱砍到最小可用——接入与部署要回答的是：v1 数据从哪来、部署物长什么样、升级怎么走，且不与「语义层写路径只有动作」（ADR-0003）打架。本 ADR 锁定七个决策点。

## 决策

1. **接入路径双轨：动作 API + 管理接入端点**：常规写入经动作 API（语义层唯一写路径不动）；批量导入经**接入端点**——管理 API 面的批量写入口，走 ADR-0002 引擎写入通道（单请求单事务、批量 ≤1000、违约束整批回滚 + 违规清单），不经动作。调用主体为服务账号（超管签发的 PAT，ADR-0004）；接入端点属管理 API 面，服务账号的接入授权由超管授予（端点形状与授权细化归 #10）。**理由**：管道/导入场景天然要绕开动作语义写全量（ADR-0004 已判），管理面暴露让「语义层写路径只有动作」与「数据要进得来」两立。**被否**：仅动作 API（大数据集导入受动作语义与 1000/批双重约束，管道场景不可用）；开放对象直写 API 进公共语义面（打破 ADR-0003 唯一写路径，权限/审计挂点重开）。
2. **CSV 归客户端 CLI**：服务端不接 CSV 解析与文件上传；`heirloom import` 类 CLI 工具把 CSV/JSON 转换后调接入端点。**理由**：CSV 列映射、编码、错误报告是客户端问题；服务端规格面保持「一个批量 JSON 端点」。**被否**：服务端 CSV 导入（上传语义、列映射 DSL、部分失败报告全套进规格，规格面翻倍）。
3. **导入审计 = 每批一条合成记录**：审计日志新增「**导入批次**」条目类型——每个接入端点请求落一条：主体、时间戳、请求 id、逐类型操作计数（create/modify/delete 各多少）、来源标记；**不记逐对象明细**。**理由**：导入是主要灌数据途径，无审计则治理轨迹开洞；逐对象明细使百万行导入产生百万审计行，首批导入即可拖垮部署。**被否**：全量逐对象审计（成本随数据量线性胀）；不审计列已知限制（与「审计=治理轨迹权威源」相悖）。
4. **外部同步器 = 模式级，无接口**：v1 规格只描述「同步器模式」——外部系统 = 外部进程，以服务账号 + PAT 认证，写入调接入端点、增量读用水位线轮询（ADR-0002）。**不留**同步器插件/框架接口位。**理由**：同步器的价值在托管运行（调度/断点/背压），无实现的接口位是无背书的契约面；模式级描述已足够让外部系统对齐。**被否**：留接口位（仿逻辑支柱先例，但逻辑的接口位是只读查询形状，同步器接口位要承诺运行时语义）；完全不提（接入端点文档缺了主要使用场景）。
5. **部署拓扑 = 内嵌 PG + 可外部**：docker-compose 起 app + postgres 两服务为零配置默认；app 只读 `DATABASE_URL`，指外部 Postgres（自建/托管）同为正式支持形态。单节点，无 HA。**理由**：自部署小团队要开箱即用，生产部署要托管数据库——两者都是真实形态，DATABASE_URL 一处抽象同时覆盖。**被否**：仅 compose 内嵌（托管 PG 用户无官方路径）；仅外部 PG（开箱即用受损）。
6. **引擎迁移 = 启动自动 + migrate-only 逃生门**：app 启动时自动检查并执行引擎 schema 迁移（advisory lock 防并发）；另提供 `migrate-only` CLI/compose 入口，供迁移账号与运行账号分离的部署手动执行。**理由**：单节点自部署最省心路径是换镜像重启即完成升级；收紧 DDL 权限的生产部署需要独立入口。**被否**：仅独立迁移步骤（升级多一步，忘跑即崩）；仅启动自动无逃生门（运行账号须持 DDL 权限，收紧部署无路径）。
7. **升级 = runbook 级，配置仅环境变量，本体 CLI 推送**：升级流程写进运维 runbook——停旧版 → `pg_dump` 备份 → 换镜像启动（迁移随启动完成）；迁移只向前，**不支持降级**；规格不自带备份机制。部署配置仅环境变量（12-factor）。**本体经 CLI 推送管理端点**（`heirloom ontology apply`）——本体是运行时定义而非部署物，与 ADR-0004「授权经管理 API/CLI」同构；本体的演化语义（版本/校验/迁移联动）归 #6。**理由**：pg_dump 是 Postgres 生态标准工具，规格无需重造；本体推送机制让演化不需要重启。**被否**：官方 backup/restore 命令（备份运维面进规格，与最小可用相悖）；完全不提备份升级（部署章缺操作闭环）；本体文件挂载启动加载（演化=重启，与运行时授权不一致）；挂载+推送双轨（优先级/冲突语义额外规格面）。

## 与 Palantir 的对齐 / 偏离

| Palantir 机制 | Heirloom v1 | 对齐/偏离 | 理由 |
|---|---|---|---|
| Data Connection 托管同步器（调度/断点/背压） | ✗ 模式级：外部进程 + 接入端点 + 水位线轮询 | ✗ 偏离 | 托管运行时规格面最重；模式级已覆盖自部署小团队 |
| 管道写入不经本体动作（dataset 分支直接落盘） | ✓ 接入端点走引擎通道，不经动作 | ✓ 对齐 | 同为「语义写走动作、管道写走旁路」双轨 |
| 全量数据 lineage/审计 | △ 导入只记批次合成记录 | △ 弱化 | 逐对象明细成本不可控；批次级足够定位责任 |
| Foundry 托管 SaaS 部署 | ✗ 自部署 docker-compose 单 PG | ✗ 偏离 | 根决策：自部署单租户 |

## 后果

- #10（API 形态）拿到输入：接入端点的线上编码（批量请求/响应形状、违规条目清单格式、导入批次查询端点）；管理 API 家族扩充——接入端点与 `ontology apply` 端点（ADR-0004 已列主体/组/授权/token 端点）；服务账号接入授权的表达。
- #6（本体定义与演化）拿到输入：本体进入部署的传输机制已定（CLI 推送管理端点）；演化语义本身（版本、与行级谓词的校验联动——ADR-0004 已移交）归 #6。
- #13（规格文档大纲）拿到输入：接入与部署章的落点——接入端点、导入审计、同步器模式、compose 拓扑、升级 runbook。
- #14（验收场景）拿到输入：端到端故事可含「CSV→CLI→接入端点→动作→审计/导入批次」链路。
- 已知限制写入规格：导入不记逐对象审计明细；无降级路径；删除不可轮询（承 ADR-0002）。
- ADR-0003「语义层写路径只有动作」表述精化：接入端点是引擎写入通道的管理面暴露，不属语义层写路径；动作仍是语义层唯一写路径。
